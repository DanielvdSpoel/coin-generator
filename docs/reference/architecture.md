# Architecture

How the Meldkamer Relatie Applicatie (MRA) is put together: what runs where, how a
request travels through the backend, how the frontend is organised, and the reasoning
behind the folder layout. This complements the high-level diagram in
`docs/architecture/mra_architecture.png` and the rules in `CLAUDE.md`; where this file
and `CLAUDE.md` disagree, this file describes the current code.

## System overview

```
 browser ── SSO gateway ──> frontend (static SPA, Vue 3)
                     └────> backend  (FastAPI, Hypercorn)
                                │
                ┌───────────────┼──────────────────┬──────────────┐
            PostgreSQL        Neo4j              Redis          Kafka
     graph metadata, users   nodes & edges    token cache,    access + audit logs
     permissions             per graph        register cache
                                │
                     external registers via gateways
                     ├─ BVI-IB (REST)      BRP, RDW, Bluespot, ...
                     └─ Superset (GraphQL) Summ-IT
```

Key idea: **two databases with a clear split**. Postgres owns everything that is
"about" a relatieschema (its title, owner, permissions, timestamps). Neo4j owns what is
"in" it (persons, vehicles, locations and their relationships). Every Neo4j node carries
a `graph_id` so the two sides join on the Postgres primary key.

Outside production, the person registers are served by `backend/fake_registers`, a
separate stdlib-only app that speaks both the BVI-IB and Superset protocols from one
committed world file.

## Repository layout

Monorepo. Two deployable apps, everything else is infrastructure:

| path | what |
|---|---|
| `backend/` | FastAPI API, Alembic migrations, tests, fake registers |
| `frontend/` | Vue 3 SPA |
| `sso/`, `sso.json`, `sso.dev.json` | SSO gateway configuration |
| `compose.yaml` + `up.sh`/`down.sh`/`build.sh`/`restart.sh` | local stack: postgres, neo4j, redis, kafka, kafka-ui, sso-gateway, wiremock, fake-registers |
| `wiremock/` | stubs for the SSO gateway, Mattermost and api health (not the registers) |
| `postgres-init/` | database bootstrap for compose |
| `.gitlab-ci.yml` | test, build and manual OTA deploy |
| `docs/` | this file, diagrams, specs, meeting notes |

Directory names are lowercase and hyphen-separated everywhere.

## Backend

### Why this shape

FastAPI imposes no structure, so the backend borrows the layering you would expect from
a "ports and adapters" style app, kept deliberately small:

```
 api/          HTTP in, HTTP out. Knows about FastAPI, status codes, request models.
   │
 core/         The domain. Knows nothing about HTTP, SQL, Cypher or the registers' wire formats.
   ├ interfaces/   ABCs + DTOs: the contracts everything else is written against
   ├ services/     business logic, implemented against the interfaces
   ├ middleware/   cross-cutting request concerns (DI, user sync, disclaimer)
   └ tools/        pure helpers
   │
 database/     Adapters for our own storage (Postgres via SQLModel, Neo4j via the driver)
 services/     Adapters for other people's systems (BVI-IB, Superset)
   │
 container.py  Wires concrete adapters into services. The only place that knows both.
```

The rule of thumb for "where does this go":

- Does it parse an HTTP request or pick a status code? `api/<domain>/router.py`.
- Is it a business rule (who may see a graph, is this a valid BSN, how do we dedupe
  persons)? `core/services/`.
- Is it a contract or a plain data shape shared between layers? `core/interfaces/`.
- Does it talk to Postgres or Neo4j? `database/repositories/`, with its SQL or Cypher as
  constants in `database/queries.py` or `database/neo4j_queries.py`.
- Does it talk to an external system over HTTP? `services/<system>/`.
- Does it need to exist before the app is constructed (config, models, container)?
  It uses stdlib `logging` instead of the Kafka logger, because the Kafka logger needs
  settings that may not be loaded yet.

### The dependency injection container

`src/container.py` is a plain Python class. Each method is a provider; the return type is
always the **interface**, never the implementation:

```python
def graph_service(self) -> GraphInterface:
    return GraphService(
        graph_repository=self.graph_repository(),
        graph_node_repository=self.graph_node_repository(),
        permission_service=self.permission_service(),
    )
```

Two lifetimes exist:

- **Singletons** are marked with `@lru_cache(maxsize=1)`: database access, Neo4j
  driver, Redis, the JWT/authentication service, the audit Kafka producer, and the
  BVI-IB / Superset HTTP repositories. These hold connection pools or caches that
  must be shared per process.
- **Per call** for everything else (services and Postgres repositories). They are
  cheap to build and stateless, so a fresh instance per request keeps them simple.

The container is created once through `get_container()`; `reset_container()` exists
for tests. FastAPI's own `Depends()` is intentionally **not** used for domain services.
Reasons: service construction stays out of the request lifecycle, test overrides are
plain Python, and the wiring is readable in one file.

### Life of a request

Middleware is registered in `configure_middleware()`. Starlette runs the last-added
middleware first, so the effective order on the way in is:

1. `UserSyncMiddleware` — resolves the user profile from the request (in dev the
   `Authorization` header is simply the employee id), upserts it into
   `application_user`, stores it on `request.state.user`, and sets two contextvars:
   the current `cn` and the caller's bearer token. Skipped for health endpoints.
2. `DisclaimerEnforcementMiddleware` — for `/api/graph*` and `/api/internal*`, returns
   403 unless the user has accepted the disclaimer. Caches accepted users in memory
   because acceptance is never reset.
3. `BurpScanBlockerMiddleware` (troi) — rejects security scanner traffic.
4. `DurationFilter` (troi) — request timing.
5. `AccessLoggerMiddleware` (troi) — structured access log to Kafka. Not added under
   pytest.
6. `DIMiddleware` — puts the container on `request.state.container` and applies
   `app.dependency_overrides` from tests onto it.
7. `GZipMiddleware`, `CORSMiddleware`.

Then the router. A typical handler does four things and nothing else:

```python
@router.get("/{graph_id}/contents", response_model=GraphContentsDTO)
def get_graph_contents(graph_id: str, request: Request) -> GraphContentsDTO:
    try:
        cn = get_userprofile(request).cn                                        # 1. who
        graph_service = get_container_from_request(request).graph_service()    # 2. resolve
        return graph_service.get_graph_contents(graph_id=graph_id, user_id=cn) # 3. delegate
    except RecordNotFoundException:                                             # 4. translate
        raise HTTPException(status_code=404, detail="Graph not found")
    except ForbiddenException:
        raise HTTPException(status_code=403, detail="Forbidden")
    except HTTPException:
        raise
    except Exception as error:
        logger.error(f"An error occurred: {error}", exc_info=True)
        raise HTTPException(status_code=500, detail=ERROR_INTERNAL_SERVER_ERROR)
```

Handlers are synchronous `def`. There is no async I/O in the request path (the
database drivers are sync), and Hypercorn runs sync handlers in a thread pool. Long
cleanup work uses FastAPI `BackgroundTasks`.

Inside the service the flow for a graph read is:

```
GraphService.get_graph_contents
  ├─ PermissionService (read check)        -> GraphPermissionRepository (Postgres)
  ├─ GraphRepository (metadata)            -> Postgres, is_deleted filtered
  └─ GraphNodeRepository (nodes + edges)   -> Neo4j
```

Services depend on other services only through their interfaces (`GraphService` takes a
`PermissionInterface`, not a `PermissionService`), and never on a repository from
another domain.

### Request-scoped user context

Services and repositories sometimes need the current user without it being threaded
through every signature (audit events, forwarding the bearer token to Superset). This
lives in `core/tools/user_context.py` as `contextvars`, set and reset by
`UserSyncMiddleware`. Handlers that need the user explicitly still call
`get_userprofile(request)` from `request_helper.py`, which also enforces authorization.

### Configuration

One `Settings` class in `core/config.py`. Fields are lowercase with local-friendly
defaults, so the app runs with no env vars against the compose stack and the fake
registers. Environment variables match case-insensitively, the local dotenv file in
`backend/` is read in dev, unknown keys are ignored.

- Derived values are properties (`is_dev`, `database_url`, `allow_cors_origins`,
  `sso_openid_connect_url`), never duplicated fields.
- Cloud Foundry bindings come in through `vcap_services`; `database_url` resolves the
  bound Postgres service and falls back to `postgres_uri`. Neo4j uses plain env vars.
- `environment` is a `Literal["dev", "integration_test", "ota", "prod"]`.
- Modules read `settings = config.get_settings()` at module level, only when they
  actually use a setting. Unit tests construct `Settings(_env_file=None, ...)`.

### Storage

**Postgres** (`database/models.py`) holds three tables: `application_user`, `graph` and
`graph_permission`. All models follow the same pattern: `XxxBase(SQLModel)` with the
fields, `Xxx(XxxBase, table=True)` adding the UUID string primary key and
`__tablename__`. Every table has `user_created`/`date_created`,
`user_updated`/`date_updated` and, except for permission rows, `is_deleted` for soft
deletes. Simple CRUD goes through SQLModel, anything with joins or paging is a raw
SQL constant in `queries.py`. Schema changes are Alembic migrations that run on every
deploy through the Procfile.

**Neo4j** (`database/neo4j_queries.py`, `repositories/graph_node_repository.py`) holds
the nodes and relationships. Every node has the shared `:GraphNode` label plus a typed
label (`:Person`, `:Vehicle`, `:Company`, `:Location`) derived from the `NodeType` enum in
`core/interfaces/graph_interface.py`, and always carries `id`, `graph_id`, `source`, `x`
and `y`. Person-like nodes store their identifications as two parallel arrays because
Neo4j cannot store a list of maps. Constraints and indexes are `SCHEMA_STATEMENTS`,
applied idempotently by the lifespan hook at startup; that is the Cypher equivalent of
`alembic upgrade head`, and it is non-fatal so a temporarily unavailable Neo4j does not
stop the app from booting.

`Neo4jAccessInterface` deliberately mirrors troi's `DatabaseAccessInterface`: a
`session()` context manager, so both kinds of repository read the same way.

**Redis** caches BVI-IB tokens (shared across processes) and register responses that
may not be persisted. `core/registers.py` states which registers are persistable
(BRP, RDW) and which are Redis-only with a TTL.

**Kafka** receives the HTTP access log and the audit events from `AuditService`.

### External registers

`core/registers.py` is the single `Register` enum and decides which backend answers
for which register: most go through BVI-IB, Summ-IT goes through Superset, GMS is not
queried yet. `PersonService` orchestrates a search:

```
PersonService.search(term, registers)
  ├─ assert registers ⊆ settings.allowed_registers
  ├─ detect_search_type: KENO (5 letters + 6 digits) or BSN (9 digits + elfproef)
  ├─ BviIbPersonRepository.search_by_keno / search_by_bsn  -> map_response_to_persons
  ├─ SupersetPersonRepository.search                      -> map to persons
  └─ deduplicate_persons (merge hits that share a key across registers)
```

`services/bvi_ib/` contains the pydantic models generated from the BVI-IB swagger, one
package per register, plus a token provider (OAuth client credentials, cached in Redis,
refresh-and-retry on 401) and a base repository holding the HTTP client. `services/superset/`
queries the "zoeken" GraphQL endpoint using the caller's forwarded bearer token and an
introspected schema under `spec/`.

### Fake registers

`backend/fake_registers` is its own small app, run with `python -m fake_registers` on
port 9006 or as the `fake-registers` compose service. It is intentionally **not** part
of the backend: stdlib logging, no troi, no `Settings`. One committed `data/world.json`
is projected onto the backend's own generated BVI-IB models and onto the introspected
Superset schema, so the fake can never drift from what the backend expects without a
test failing. Integration tests mount it in-process through `TestClient`, so no
container is needed for register tests. Its README documents the world, the
projections and the dedup contract between registers.

### Tests

- **Unit** (`tests/unit/`): `unittest.TestCase`, every collaborator is
  `Mock(SomeInterface)`. This is why every service has an ABC: it is the thing you
  mock.
- **Integration** (`tests/integration/`): one Postgres testcontainer per test class
  with real Alembic migrations, a Neo4j testcontainer for graph repository tests,
  `TestClient` against the real app factory, fake registers in-process, and
  `app.dependency_overrides` to swap infrastructure. `DIMiddleware` maps override keys
  onto container providers through its `name_map`.

## Frontend

### Shape

The SPA follows the standard Vue 3 layout, with one convention layered on top: **data
flows down through stores, HTTP is confined to services**. Components never call
`fetch`, and stores never contain rendering concerns.

```
 views/          one component per route (HomePageView, GraphView)
   │
 components/     Home/  and  Graph/  feature folders, plus generic/ (TROI-prefixed)
   │                Graph/ is split by UI region: ActionsToolbar/, ViewToolbar/, Render/
   │
 composables/    behaviour reused by components: useNodePositionPersistence,
   │             useGraphLayout, useEntityImport, useLayout
   │
 stores/         Pinia: graphs (list), graphContents (canvas state), user (profile + disclaimer)
   │
 services/       graphService, personService, userService: plain async functions
   │             over jsonFetcher; TypeScript interfaces mirror the backend DTOs
   │
 services/utils/Fetcher.ts   the only place that calls fetch()
 utils/          pure helpers: casing, date (Luxon), env, hash, layoutPreference, matomo
```

### How the canvas works

`GraphView` loads a relatieschema into `useGraphContentsStore`, which keeps the domain
nodes and relationships exactly as the API returned them. Two getters,
`vueFlowNodes` and `vueFlowEdges`, translate them into Vue Flow's `Node` and `Edge`
shapes; the domain node travels along as `data` so `EntityNode.vue` can pick its icon
and label from `Render/nodeTypeConfig.ts`. Every entity uses one Vue Flow node type
and one custom edge type (`CenterEdge`), keeping the rendering config in two small
files instead of per-type components.

Position changes go the other way: `useNodePositionPersistence` listens to Vue Flow
drag events, marks nodes dirty in the store, debounces, and calls
`updateNodePositions` in `graphService`. Auto-layout (`useGraphLayout`, dagre) writes
new positions into the same store and toggles `isLayoutAnimating` so the canvas can
animate the move with CSS.

### Services and mocking

`Fetcher.ts` wraps native `fetch`, sends credentials by default, and throws the
`Response` object on non-2xx so callers can inspect the status. Service modules export
functions only. `graphService` has a mock mode for the graph-contents endpoints
(`VITE_MOCK_API`, `?mock` on non-prod) so the canvas can be developed while the backend
changes; it is never active on prod.

### Routing and auth

`router/index.ts` has two routes: `/` and `/schema/:id`. A global guard calls
`userStore.ensureUser()` and sends anyone who has not accepted the disclaimer back to
the home page, which shows it. The backend enforces the same rule in
`DisclaimerEnforcementMiddleware`, so the guard is a convenience, not the security
boundary. Authentication itself is handled by the SSO gateway web component in front
of the app.

### Build and runtime config

Vite builds a static bundle deployed with the Staticfile buildpack. Runtime settings use
`VITE_*` variables whose values are `__VITE_*__` placeholders in the bundle, replaced by
CI before `cf push`, so one build serves every environment. The current release hash is
read from `/version.txt`, written into `dist/` at build time. User-facing release notes
live in `src/release-notes.json`.

## Deployment

GitLab CI runs `test` (secret detection, backend unit + integration with Docker-in-Docker,
frontend vitest), `build`, then manual jobs that create the OTA space and `cf push` the
backend, frontend and SSO gateway from their `manifest.yml` files. The backend Procfile
runs migrations before starting Hypercorn, so a deploy never needs a manual migration
step. Neo4j schema is applied by the app itself at boot.
